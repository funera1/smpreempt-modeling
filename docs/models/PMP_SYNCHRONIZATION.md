# PMP同期不足によるHost単独攻撃

## 根拠となる仕様

参照はRISC-V公式の
[Machine-Level ISA v1.13 / Physical Memory Protection and Paging](https://docs.riscv.org/reference/isa/v20260120/priv/machine.html)
および
[Supervisor ISA v1.13 / satp](https://docs.riscv.org/reference/isa/v20260120/priv/supervisor.html)。

VMを備える実装はBareの恒等変換とPMP判定結果もキャッシュし得る。
PMP更新後は全体SFENCE.VMAによる同期が要求される。
ページベースVMを実装しないhartではPMPを同期的に検査するため、この同期は不要。
satp書込み自体は変換キャッシュの無効化を意味しない。
ページテーブルウォークの物理アクセスにもPMP検査が適用される。

以下は仕様が許す挙動の代表的な抽象モデルであり、全TLB実装の再現ではない。

## 第1段階の分類

| クラス | 現在の扱い |
|---|---|
| A. 現在のPMPによる保護メモリの直接R/W | attacksモードで実装済み |
| B. 古い許可結果によるアクセス | pmp-syncモードを追加 |
| C. CPU状態の露出 | GPRの初期化・復元は既存の候補機構。全CSRは未対応 |
| D. 保護メモリの不正実行 | データ攻撃とは分離。命令フェッチは未対応 |
| E. 保存コンテキストへのアクセス | 保存スロットは引き続き抽象的に保護済み。物理配置との対応は未実装 |

PMP変更途中・優先順位・範囲設定の問題はAの成立原因としてまとめる。
Bは現在のPMPの検査だけでは検出できないため、実効アクセス判定が必要になる。

## 状態と遷移

具体モデルVに `cache_pmp_permissions` と代表エントリ `cached` を追加した。
既定値Falseは従来の同期的PMP抽象化を維持する。
TrueはVMを備えるhartで、Bare中もPMP判定をキャッシュし得るモデルを選ぶ。
VM非搭載hartにおけるSFENCE命令の実装有無は、このフラグでは表現しない。

エントリはVA/PA、アクセス範囲、実効特権、過去PMPのスナップショット、生成元のアクセス種別を持つ。
記号モデルではvalid・範囲・特権・R/W/Xの判定結果を保持し、生成時に過去PMPから権限を導出する。
初期キャッシュは任意の権限ビットを与えるのではなく、具体的な合法アクセスまたは
指定した過去PMPからの合法なS-modeアクセスで生成する。

| 操作 | キャッシュの扱い |
|---|---|
| pmpcfg0 / pmpaddrへのCSRW | PMPだけを更新。エントリは残る |
| satpへのCSRW | satpを更新。エントリを自動消去しない |
| SFENCE.VMA x0,x0 | 代表エントリとプレースホルダTLBを無効化 |
| 成功したデータアクセス | 現在PMPからキャッシュを生成し得る |
| キャッシュヒット | 過去に得た許可/拒否結果を使用し得る |

古い結果を使うかは記号変数use_cachedで選択する。ミスなら現在PMPを使う。
キャッシュを新規生成するかもfill_cacheで選択し、キャッシュを持たない実装や置換の省略を表す。
VA/PAはこの段階では恒等写像、実効特権が一致し、要求範囲を覆うエントリだけがヒットする。
M-modeの未ロックPMP迂回による許可を、そのままS-modeへ流用することは認めない。
同一範囲でも読取許可から書込許可を捏造せず、元のPMPの各権限に従う。

具体step/Machine.instructionはuse_cachedとfill_cacheを引数で受け取る。
記号BMCは各命令境界で両者を選ぶ。エントリは1件なので全置換方式を網羅しない。

## PMとの接続

PMに `sync_pmp=True/False` を追加した。既定はFalse。
Trueなら、Host用PMPの設置後、および再開用PMPの復元後に全体同期する。
Falseでは、Host用satpをBareにするだけでキャッシュを消してはいけない。

ハードウェアキャッシュはソフトウェアが保存スロットから復元できるものとは扱わない。
保存するVはsatpの構成値であり、再開時も現在のキャッシュを維持するか、明示的に無効化する。
保存時のキャッシュを再投入しない。
isolation制御の判定も、キャッシュ有効モデルでは新旧どちらかの権限でアクセスできる可能性を検査する。

## 比較実験

```sh
.venv/bin/python -m smpreempt.exploration.explore_system --analysis pmp-sync
```

同じ初期条件で同期なし・ありを比較する。

1. 過去のPMPは0x8000へのS-mode読取/書込を許す。
2. Hostが公開値0を読んだ結果から、S-modeの代表キャッシュを生成する。
3. SMが新しいデータ0xA5を書き、現在のPMPを安全な設定に更新する。
4. 中断時点ではPMP CSRは0x8000へのHost R/Wを拒否している。
5. PMがHost用PMPを設定し、SFENCEを入れる場合と省く場合を比較する。
6. SMを再開せずHostのLBU/SBでアクセスを試す。

このCLIでは中断時PMPを安全テンプレートに固定し、Aは0x8000だけとする。
代表エントリのVAは記号変数だが、攻撃成立には対象へのマッチが必要。
各攻撃は `現在PMPでは拒否 ∧ 実効アクセスでは許可` も要求して、クラスAを除く。

結果:

| PM | 読取 | 実際の書換え |
|---|---|---|
| 同期なし | sat、キャッシュ経由で0xA5を読む | sat、キャッシュ経由で0xA5を変更 |
| 全体SFENCEあり | unsat | unsat |

同期ありでもHost入口は実行可能であり、Hostを動かせないことによる自明なunsatではない。
これはこの代表モデルと初期条件に対する結論で、あらゆるキャッシュ実装に対する十分性証明ではない。

## 来歴の確認と反例の出力

反例にはprior_traceとhost_traceを出し、projection_replayedに加えてcache_provenance_replayedを表示する。
過去のS-mode LBU、SMのSB、pmpaddr/pmpcfg CSR更新、PMのsatp設定と必要ならSFENCE、
最後のHost LBU/SBを具体命令モデルで再実行する。
過去にHostが読んだ値0と、SMが後で書いたデータ0xA5を分け、単に既知の値を再読する例にしない。
コンテキストの正規入口と命令フェッチは引き続き抽象化している。

cache_origin_pmpを指定したAPIの来歴再実行は、現在は未ロックの過去PMPに限定する。
過去PMPから中断前PMPへ設定できることも検査する。
任意配列全体・Aの全履歴・実機TLB・特定SMの実行を再現したという意味ではない。

## 記号BMCの命令対応

全体BMCにも代表キャッシュと動的satpを接続した。
SFENCE.VMA x0,x0とCSRW satpを扱い、PMP CSR更新ではキャッシュを維持する。
選択的SFENCEは未対応として拒否する。
実効特権がS/Uかつsatp≠0のメモリアクセスは、Sv39/WARL等未実装なのでunsupported終端とし、
探索結果を安全とは扱わない。M-modeの通常物理アクセスはsatpに依存しない。

次は、より広いキャッシュ来歴、命令フェッチ/X、CPU/CSR状態の露出、保存領域の物理配置、
必要に応じたSv39ウォークを順に検討する。
