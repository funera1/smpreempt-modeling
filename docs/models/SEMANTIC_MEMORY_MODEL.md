# アクセス履歴から意味に基づくメモリ安全性への移行

## 結論と実装状況

保護対象を `A` や別の固定集合 `R` として定義し直すのではなく、秘密への依存と、将来の信頼された使用に対する影響から、時点ごとの読取・書込制限を導出する。
その後で、PMがその制限を実効アクセス権として実現できるかを検査する。

これは新しい研究仕様の提案である。既存の統合探索器の安全性条件はまだ `A ∪ R_fixed` のまま。
[実験](../../experiments/semantic_requirements.py) は既存の命令意味論を再利用した経路限定の記号実験であり、統合済みの全経路検証器ではない。

## 現行コードでできることと不足

| 構成 | 現在できること | 新しい問題に対する不足 |
|---|---|---|
| `riscv_model.py` | メモリ・GPR・PMP更新、保存復元、代表権限キャッシュ | 秘密入力、正当な公開、信頼された使用の意味がない |
| `symbolic_instructions.py` | LD/SD、演算、分岐を配列・ビットベクトルで記号実行 | 情報源や使用契約、二実行の比較がない |
| `symbolic_system.py` | SM→PM→Host→PM→SM、Host書換え、動的PMP、有限深さBMC | 判定がHost時点の領域露出。再開後の値の意味を検査しない |
| `host_attacks.py` | 任意中断状態から合法なHost読取・変更を探索 | SMの前後を接続せず、実際の漏えい・不正使用を識別しない |
| `symbolic_pmp.py` / `symbolic_cache.py` | 権限判定、ロック、更新、古い許可とフェンス | 意味から要求を導く機能、PMP合成はない |
| `preemption.py` | 固定PMと許可条件を検査 | `isolation` は既存の領域ポリシーの十分条件であり、新仕様の導出ではない |

ケースAの「公開→消去」という命令順序は表せる。しかし、消去後も履歴は残り、読まれても秘密に依存しないことを判定できない。
ケースBのHost変更と再開は表せる。しかし、上書きで無害化されるか、使用前に検証されるか、再読込みで検証が失効するかを安全性条件が区別しない。
任意状態の初期メモリが記号的であることと、プログラムの秘密入力を記号実行することも別である。

調査中に、統合BMCの反例再検査がfresh PMPのみを使い、キャッシュだけで許可される反例でAssertionErrorになり得る点も確認した。代表キャッシュの個別解析とは別の問題で、修正はTODOに残す。

## 最小限必要な仕様

コードだけでは、同じビット列が秘密か公開値か、同じ使用が正当か不正かは決まらない。次を明示する。

1. 秘密の入力イベント・引数。アドレスではなく入力値の意味を指定する。
2. 公開入力と初期Hostメモリ。初期Hostメモリは任意値とし、善意のゼロ初期化を仮定しない。
3. 信頼された使用イベントと許容値・許容関係。例は「この使用では値が0」「使用値が検証された値と一致」。
4. 拒否として許される挙動、公開出力、必要になった段階での正当な公開イベント。

検証済みというBooleanを無条件に仮定しない。実際のロード・比較・分岐で契約成立を確認する。
検証証明をメタデータ化する場合は対象値・版に結びつけ、関係する書換えで失効させる。

## 機密性：同じ公開入力を持つ二実行

同じコードと公開入力を使い、秘密入力だけ異なる二つのSM実行を中断点まで進める。
初期の公開メモリ配列は共有する。PC、レジスタ、メモリは各実行で別に持つ。

最初の実験では秘密依存のない固定中断点と、意図的公開のないコードに限定する。
そこでのバイト読取要求は、権限を掛ける前の反実仮想的な読取から導く。

`NeedDenyRead(a,k) := ∃ public, secretL, secretR. PrefixL(k) ∧ PrefixR(k) ∧ ML[a] ≠ MR[a]`

これはアドレスを一つ指定して保護する仕様ではない。コードが秘密を格納した先を記号実行から求める。
現行PMPが拒否するから「保護不要」と結論しないよう、意味上の要求とハードウェア制限を分離する。

実際の攻撃ではHost観測を比較する。観測には読取値だけでなく成功・faultも含める。
秘密依存の許可マスクはfault自体から漏れる可能性があるため、値の相違だけでは一般的な非干渉性の証明にならない。
秘密依存の分岐・中断時刻を扱う段階では観測時点の対応も仕様化する。現在の実験は扱わない。

ゼロ消去後はメモリ値が秘密に依存しなくなるため、特別な「公開済み」フラグは不要。
正当な公開を導入する場合は、その観測時点までに公開してよい情報だけを等価性から除く。将来公開される予定という理由では許可しない。
この二実行による整理は非干渉性の考え方に基づく。公開の扱いの背景は [Robust Declassification](https://www.cs.cornell.edu/zdance/robust_declassification.htm) を参照。

## 完全性：Host書換えと将来の使用

同じ初期入力に対して、Hostを挟まない参照実行と、中断後Hostが書き換えてから再開する攻撃実行を比較する。

`Attack(k) := Prefix(k) ; HostWrites ; Resume ; Suffix`

`BadUse` は使用イベントで契約を破ること。単なるメモリ値の変更や全出力の不一致を脆弱性とはしない。
共有入力の合法な変更や拒否経路は、契約で許される場合には不正使用に数えない。

まず権限を外したHost書換えで `BadUse` を生むアドレス・値・使用箇所を探索し、その後で実効書込許可を加える。
初期化前の書換えは後の初期化で消える。一方、初期化後から使用前の書換えは残ることがある。
検証後にメモリを再読込みする実装はTOCTOU候補だが、検証した保存レジスタ値を使うだけなら同じ書換えは無害である。

プリエンプションなしでも初期Host値を不正使用する場合は基準実行の脆弱性として別報告する。
`RefSafe ∧ AttackBad` は同じ初期状態での追加攻撃機会の証拠になるが、基準実装全体の安全性を証明したことにはならない。

単一バイト書換えによる反例集合から、一般の任意回書換えに対する必要十分な禁止集合は得られない。
複数書換えでのみ成立する攻撃には、変更集合の少なくとも一箇所を防ぐ組合せ制約が必要な場合がある。
一般化時はHostに書込可能な任意バイトを任意値へ変更するフレーム関係を与え、保存値との関係を保持する。

## PMP・PM・地点制御への接続

意味上の攻撃条件と、実効アクセス権を結合する。
読取と書込の要求は別々で、時点ごとに変わる。一時的なPMP緩和も、所有権移譲という専用イベントなしで同じように扱える。

候補PMについて、許可されるHost操作では漏えい・不正使用が存在しないことを調べる。
PMPの粒度・エントリ数・優先順位・ロック・設置復元可能性、古い権限キャッシュと同期も別に満たす必要がある。
さらにHostの実行入口・必要作業領域・再開後の機能性を満たす。全メモリ拒否や無条件消去だけで研究目的を満たしたことにしない。

PM合成の目標は `∃ 実装可能な方策 f. ∀ 状態・入力・Host操作. Safe(f(O), ...)`。
`∀ 状態. ∃ 設定` だけでは、PMが観測できない秘密や未来を使う設定選択を許してしまう。
最初は具体的な候補PMごとに安全性を検査し、合成は後段にする。

安全な候補PMが実現できない中断点では延期を検討する。ただし「候補一つが失敗」と「許された全PMで不可能」は区別する。
地点制御の範囲・最大延期時間にはCFGと到達可能性・ループの進行性が必要で、任意スナップショットだけからは求まらない。

## 最小実験と実行結果

実行: `python3 -m experiments.semantic_requirements`

既存の記号LD/SD/BEQと配列メモリを使用。2ワードの格納・消去、任意の初期公開メモリ、記号的な秘密値とHostの単一バイト書換えを扱う。
プログラムの引数がデータのアドレスを決めるが、そのアドレスを保護対象という注釈では与えていない。A/Rは安全性式に使わない。

| 問合せ | 結果 |
|---|---|
| 秘密格納後、Hostに読取許可 | 漏えい反例あり |
| 2ワード中1ワードのみ消去後、読取許可 | 漏えい反例あり |
| 全消去後、読取許可 | この実験では漏えい反例なし |
| 消去前でもPMPで読取拒否 | この実験では漏えい反例なし |
| Host書換え後に全初期化して使用 | 不正使用反例なし |
| 初期化→Host書換え→使用 | 不正使用反例あり |
| 初期化後でもPMPで書込拒否 | この実験では不正使用反例なし |
| 初期化なしで使用する基準実行 | 元から不正使用反例あり |
| 検証→Host書換え→再読込み | TOCTOU反例あり |
| 検証→Host書換え→保存した検証値を使用 | この実験では反例なし |

`sat` は反例あり、`unsat` は指定した式に反例なし。期待結果はスクリプト内で照合し、unknownも失敗扱いにする。
TOCTOUはBEQの受理側経路だけを検査しており、拒否側を含む全CFGは未検査。
キャッシュ、複数Host書換え、SM再入、意図的公開、秘密依存の制御フローはこの実験に含まない。

## 統合までの作業

1. 安全性式を統合BMCの遷移定義から分離する。既存A/R検査は旧ポリシーとして保持する。
2. 記号初期入力と、各実行で衝突しない変数名を導入する。現状の `s1` / `t0` を二実行で共有しない。
3. 秘密入力、公開観測、信頼使用の契約をシナリオに追加する。
4. prefix・中断・任意Host操作・suffixを接続し、上記実験を分岐を含むBMCに移す。
5. baseline/追加攻撃/モデル未対応/深さ不足/unknownを別報告する。使用まで届かない経路を安全扱いしない。
6. 意味上の必要制限と候補PMの実効権限を接続し、キャッシュ・同期を含めて検査する。
7. PMP資源、拒否権限、延期区間を評価する。無上限保証には帰納的不変条件や契約の保存性が必要。

任意スナップショットK0はハードウェア実現可能性の過大近似として引き続き使える。
ただし、そのビット列が何に依存し、将来どう使われるかはK0だけでは決まらない。
意味を導出する段階にはコードの実行関係、またはそれを要約する証明済み契約が必要である。
